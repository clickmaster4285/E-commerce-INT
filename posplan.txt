## 4. AUTH & ROLES

- **Mechanism:** Custom JWT access/refresh tokens. Backend reads a Bearer token or `accessToken` cookie in `backend/middleware/authMiddleware.js`; login code sets `accessToken` and `refreshToken` cookies in `backend/controllers/userController.js`. Cookie options in the inspected code include `httpOnly: true`, `sameSite: "lax"`, and `secure: false`.
- **Identity split:** Customer accounts are in `User`; admin/staff accounts are in `Employee`. Admin login checks Employee roles `admin`, `staff`, or `manager`. The User schema also has a role enum, but the admin login path uses Employee.
- **Roles found:** `admin`, `staff`, `manager` in Employee; User schema also permits `user`, `admin`, `staff`.
- **Permission system:** Boolean permission properties on Employee; `checkPermission(key)` is in `backend/middleware/checkPermission.js`. Admin bypasses checks; staff are denied only when the requested permission is explicitly `false` (undefined is allowed). There is also `staffPermissionCheck` and `adminMiddleware`.
- **Admin route protection:** `frontend/middleware.js` checks only for an `accessToken` cookie before allowing `/admin...` pages; it does not validate the JWT itself. Actual API token verification occurs in backend auth middleware. `frontend/src/app/admin/layout.js` fetches the profile, checks admin role/permissions, and redirects unauthorized users.
- **Where the admin check is done:** In backend `loginAdmin` for Employee role eligibility, in `checkPermission` for API permission bypass, and in the admin layout for page permissions. Sidebar visibility is separately calculated in `frontend/src/components/adminComponents/Sidebar.js`.
- **Permission wiring caveat:** `users` exists as an Employee permission, but no admin customer page/route uses it. Sidebar/layout route-permission entries do not include a customer route.
- **Permission schema mismatch:** `vendors` and `purchaseOrders` appear in seed/controller permission handling, sidebar entries, and guarded backend routes, but are absent from the explicit permission fields in the Employee schema. Confirm intended behavior before relying on those permissions.
- **Authorization inconsistency:** Some resource routes, including discounts and tags, require authentication but do not call `checkPermission` for their admin operations; new modules should not assume sidebar hiding alone enforces access.

## 8. REUSABLE PATTERNS

- **API style:** REST over Express; controllers call Mongoose directly. No service or repository layer found.
- **API clients:** Shared Axios setup in `frontend/src/apis/axiosInstance.js`, plus resource wrappers under `frontend/src/apis/`. Axios sends credentials, refreshes on 401, and emits user-session-expired events; the admin client redirects to admin login after refresh failure.
- **Responses:** Common shape is `{ success, data, message }`; paginated order lists also return `pagination`. Some handlers return only `{ message }` or add resource-specific fields, so response shape is not universal.
- **Validation:** Controller-level checks and Mongoose schema constraints; no shared Joi/Zod validation layer found. Phone validation helper and upload/image validation middleware exist.
- **Errors/logging:** Controllers generally catch and return JSON errors; a standard global Express error handler was **NOT FOUND**. The `log` methods in `backend/utils/logger.js` are no-ops, so calls through that logger do not emit errors. Some startup messages use `console`.
- **Pagination/search:** Resource-specific query patterns. For example, admin order listing supports page/limit and returns total/page/totalPages; filtering/search are controller-defined, not a shared framework.
- **Uploads:** Multer plus local storage under `backend/uploads`, served statically at `/uploads`. Product images use in-memory upload plus Sharp metadata/processing; upload configurations are present in both `backend/config/uploadConfig.js` and `backend/middleware/uploadConfig.js`.
- **Realtime:** Socket.IO server in `backend/utils/socket.js` and client hooks in `frontend/src/hooks/`.
- **State:** TanStack React Query for server data; Redux Toolkit has one `storeInfo` slice in `frontend/src/redux/store.js` and `frontend/src/redux/slices/storeInfoSlice.js`. Storefront also has React Contexts for cart, wishlist, discounts, and quick buy. Zustand is a dependency, but actual Zustand usage was **NOT FOUND**.
- **Configuration:** Backend config in `backend/config/`; frontend config includes `frontend/next.config.mjs`, `frontend/tsconfig.json`, `frontend/postcss.config.mjs`, `frontend/eslint.config.mjs`, and `frontend/components.json`. TypeScript is permitted by config, but application source is JavaScript.
- **Environment:** `.env` files exist in both apps; their values were not inspected. `.env.example` was **NOT FOUND**. Code reads settings including `MONGO_URI`, `JWT_SECRET`, `API_PREFIX`, `PORT`, `HOST`, CORS origins, rate-limit/Redis, SMTP, upload limits/paths, and `NEXT_PUBLIC_SERVERURL`/`NEXT_PUBLIC_SOCKET_URL`.
- **Localization:** i18n framework or translation resources were **NOT FOUND**. Root document declares `lang="en"`.
- **Naming:** Mixed conventions: JavaScript camelCase filenames and PascalCase model files, with `brand.js` as a lowercase exception; database fields mix snake_case and camelCase.

## 9. GAPS & RISKS

1. **POS is not present:** No POS page, API, cashier/session model, tender/payment record, sales receipt/invoice model, or printer/payment-provider integration found.
2. **Order schema is e-commerce-specific:** `Order.user_id` is required and `address_snapshot` requires customer/address fields. Existing `placeOrder` looks up an address belonging to the authenticated user. POS cannot assume this flow supports guest/counter sales.
3. **Pricing must be re-evaluated for POS:** Existing order code documents a frontend-snapshot pricing flow. Reusing it for cashier sales without server-side price/discount validation would carry that assumption into POS.
4. **Customer administration is missing:** `User` already represents customers and supports self-service features, but no admin customer directory/detail/API was found. The Employee `users` permission alone does not implement it.
5. **Permission wiring needs care:** Add backend authorization as well as sidebar/layout entries. `checkPermission` permits a permission that is undefined; the frontend sidebar generally requires explicit `true` for non-admins. The `vendors`/`purchaseOrders` schema mismatch is another warning.
6. **Tenant/branch support is incomplete or unverified:** Store references exist on User, Employee, and Banner; Category has an optional `tenant_id`, but no Tenant model was found and category code comments/queries indicate tenant filtering was removed. Product, Variant, Order, and stock schemas do not show consistent store/branch scope. **Branch support: NOT FOUND.**
7. **Currency:** Store has a single `currency` setting (default PKR). Currency conversion or per-sale multi-currency handling was **NOT FOUND**.
8. **Dangling schema references:** `Tenant`, `Collection`, and `Size` references have no matching model definition in the repository.
9. **Logging/error handling:** The shared logger is silent/no-op and no global error middleware was found; this reduces operational visibility for new module failures.
10. **Inconsistent authorization and naming:** Some authenticated CRUD routers do not enforce a resource-specific permission; field and timestamp naming varies between modules.
11. **Environment/deployment certainty:** No example env file or deployment configuration found. Actual `.env` values and production hosting cannot be verified from this audit.
12. **Test coverage:** Backend `test` script is a placeholder that exits with “no test specified”; no frontend test script was found.
13. **Current working-copy caveat:** The audit began with many pre-existing modified/deleted files. In particular, `frontend/package.json` declares a `warmup` script, while `frontend/scripts/warmup.js` is deleted in the current working tree, so that script will not run as currently checked out.

## 10. INTEGRATION POINTS FOR POS + CUSTOMERS

- **Frontend routes:** Natural locations are `/admin/pos` and `/admin/customers` (with a customer detail route if required), under `frontend/src/app/admin/`.
- **Sidebar/layout:** Add menu items and sections in `frontend/src/components/adminComponents/Sidebar.js`; add route-permission mapping in `frontend/src/app/admin/layout.js`. Employee has an existing `users` permission key, but no customer route currently uses it. A new POS permission key would need consistent schema, seed, menu, layout, and backend wiring.
- **Backend routes:** Add route groups and mounts in `backend/server.js` under its configured `API_PREFIX`. Names such as `/pos` and `/customers` are possible integration paths, not existing routes.
- **Customer data reuse:** Use existing `User` customer records rather than creating a duplicate customer collection by default. Related data already lives in Address, Order, Review, Cart, Wishlist, and CheckoutDraft. Customer tags/notes/segments/loyalty records are **NOT FOUND**; whether they require additional models depends on intended customer-management scope.
- **POS inventory/product reuse:** Product and Variant provide catalog, SKU, price, and quantity; StockHistory supplies inventory adjustment history. Orders decrement Variant quantity; stock adjustment and purchase receiving also update inventory. POS sales must update stock consistently and preserve an audit trail.
- **Orders/payments:** Existing Order can store line snapshots and order statuses, but has required e-commerce customer/address assumptions. It stores a payment method/status, not a dedicated payment/tender ledger. A POS design must decide whether to extend Order with a channel/cashier/counter-sale model or create a distinct sale record. Sessions/shifts, multiple tenders, refunds, and receipt records have no current model; add only if required by the POS workflow.
- **Pricing reuse:** Existing deals, discounts, bundles, tax configuration, and frontend calculator helpers may be reusable. Verify that final POS pricing is computed/validated on the backend rather than trusting a browser-provided total.
- **Reusable UI/data patterns:** Reuse the admin layout/sidebar, Axios admin client, React Query, Sonner, custom HTML table/form style, and existing product/variant selection patterns. Reuse stock and order socket patterns if POS needs live inventory/order updates.
- **Printing/payment constraints:** Sales invoice/receipt generation and payment-provider integration were **NOT FOUND**. The only invoice-like field located is purchase-order receiving `invoice_no`.
